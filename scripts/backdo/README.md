# BackDo의 실행 기록과 복원

BackDo는 빌드된 `devtools-frontend` 웹 화면이다. 실행 위치의 순서를 기록하고, 대상 프로세스를 처음부터 다시 실행하여 직전 위치로 돌아간다. 변수·힙·클로저의 스냅샷은 저장하지 않는다.

## 기존 사용 방식과 현재 연동 범위

- 브라우저: 기존 `devtools_app.html?ws=...` 화면의 Console에 `debugger;`와 코드를 입력한다.
- 웹페이지: `inspector.html?ws=...`로 연결한 페이지의 스크립트를 디버깅한다. 같은 공통 모듈을 사용한다.
- Node: 사용자가 자신의 터미널에서 `node --inspect-brk <cli.js>`를 실행한다. `/json/list`에서 확인한 주소를 `js_app.html?ws=127.0.0.1:9229/<ID>`로 전달하는 기존 방식은 유지한다.

BackDo는 사용자에게 파일 경로나 실행 명령을 요구하지 않는다. 이전에 추가했던 실행용 `debug.ts`와 전용 `DebugServer.ts`는 제거했다. `tests/NodeTestTarget.ts`와 `tests/BrowserTestTarget.ts`는 테스트가 소유한 프로세스만 실행하는 도우미다.

**실제 서비스의 프로세스 재시작·포트 조회 연동은 아직 남아 있다.** 프런트엔드에는 `ReplayConnection.setLifecycle()`로 두 동작을 연결하는 경계만 마련했다. 외부 `server` 저장소는 변경하지 않았다.

| 입력·동작 | 현재 프런트엔드 처리 |
| --- | --- |
| `?ws=...`, `?wss=...` | 기존 WebSocket에 직접 연결 |
| `?port=9229` | 주입된 `discover(port, kind)`에 포트만 전달; 연동이 없으면 안내 |
| 뒤로가기 | 주입된 `restart({ws, kind, pageURL?})`에서 새 WebSocket을 받아 연결 교체 |
| 재시작 연동 없음 | 기존 디버깅·기록은 유지, 뒤로가기 버튼 비활성화 및 사유 안내 |

포트 번호만으로 브라우저 JavaScript가 OS 프로세스를 재시작할 수는 없다. 다른 출처의 Node `/json/list`를 브라우저에서 직접 조회하는 실험도 CORS로 차단됐다. 따라서 후속 서버 연동은 포트 조회와 재시작을 실제로 제공해야 한다. 특정 HTTP 경로를 미리 가정하지 않는다. 통합 테스트에서는 이 두 동작을 테스트 전용 함수로 주입했다.

## 공통 실행 흐름

```text
기존 콘솔 / Node ws 연결 / inspector 웹페이지
                         ↓
        ReplayConnection: 대상과 연결 구성
                         ↓
    ReplayController: 일반 브레이크포인트 설치
                         ↓
    ReplaySession: 위치·순서 기록, Step·Resume 판단
                         ↓
          뒤로가기 버튼 → 직전 위치 선택
                         ↓
  외부 연동으로 대상 재시작 → 새 WebSocket에 연결
                         ↓
     같은 문서에서 history.replaceState로 주소 갱신
                         ↓
 콘솔 원문 다시 제출 / 웹페이지 이동 / Node 실행 재개
                         ↓
     매 정지의 소스 해시·줄·열·순서를 기록과 대조
                         ↓
        목표 정지만 UI에 전달하고 화면 전환
```

`history.replaceState`는 실제 연결이 응답한 뒤 적용한다. BackDo 문서와 `history.state`를 유지한다. 중간 정지는 SDK에서 소비하므로 Sources 패널에는 최종 정지만 전달한다.

브라우저와 Node가 별도 복원 엔진을 갖지 않는다. 대상별 차이는 연결 종류와 시작 입력에 한정한다. 웹페이지 재시작은 기존 페이지 URL로 다시 이동하며, 콘솔 입력은 원문과 입력 시점을 다시 제출한다. 콘솔에서 먼저 준비 코드를 실행한 뒤 디버깅 코드를 입력하는 경우도 테스트했다.

## 기록의 수명과 용량

기록은 **프런트엔드 메모리**에만 보관한다. 시간 경과나 장시간 일시정지만으로 만료하지 않는다. 실행 컨텍스트 교체, 새 대상 연결, 종료·실패 때 해제한다. 제어된 복원을 위한 재연결에서는 목표에 도달할 때까지 유지한다.

| 항목 | 상한 | 의미 |
| --- | ---: | --- |
| 방문한 실행 위치 | 100,000개 | URL·소스 해시·줄·열. 같은 위치를 반복 방문해도 각각 계산 |
| 콘솔 입력 | 256개 | 이전 입력도 순서대로 재실행하기 위한 원문 |
| 콘솔 원문 | 4MiB | `문자열.length × 2`로 산정한 예산; 실제 힙과 동일하지 않음 |
| 기록용 브레이크포인트 | 20,000개 | 서로 다른 정지 가능 위치 |
| 식별 대기·보관 중인 콘솔 소스 | 256개 | 익명 스크립트 식별 결과의 누적 제한 |

상한 중 하나를 넘으면 위치·복원 계획·콘솔 원문·소스 매핑을 함께 해제하고 기록용 브레이크포인트를 제거한다. 앞부분만 지우면 처음부터의 경로를 검증할 수 없으므로 **해당 실행 기록 전체를 종료**한다. 일반 디버깅은 계속 사용할 수 있고, 뒤로가기는 비활성화한다. 툴팁과 오류 안내에는 다음 사유가 들어간다.

> 실행 기록 한도에 도달해 뒤로가기를 사용할 수 없습니다. 뒤로가기가 필요하면 디버깅 세션을 다시 시작하고, 가능하면 실행 범위를 줄여 원하는 위치까지 이동해 주세요.

Resume도 내부에서는 모든 방문 위치를 기록한다. 따라서 클릭 수를 줄이는 것만으로 기록량이 줄어들지는 않는다. 입력 데이터·반복 횟수·실행 경로를 줄이는 것이 도움이 된다. **소스 1,000줄과 위치 1,000회 방문은 다르다.** 짧은 반복문도 많은 기록을 만들 수 있다.

복원 중 30초 동안 진행이 없으면 응답 없는 연결·대기 작업을 실패 처리한다. 진행이 있으면 대기 제한을 갱신한다. 이것은 기록의 보관 시간이나 복원 총시간 제한이 아니다.

## 측정 결과

Node 22.11.0, macOS arm64, Chrome 156.0.8078.81에서 측정했다. 측정 결과는 이 환경의 표본이며 모든 기기의 보장은 아니다.

위치 배열의 증분 힙은 실제 Chrome에서 `HeapProfiler.collectGarbage` 이후 `Runtime.getHeapUsage`로 3회 측정했다. 같은 소스의 URL·해시 문자열을 공유하는 경우다. 모듈 로딩과 초기 실행 비용을 제외한 기준값 대비 증가량이다.

| 방문 위치 수 | 위치 배열의 증분 힙 |
| --- | ---: |
| 1,000개 | 약 33–37KiB |
| 10,000개 | 약 318–322KiB |
| 50,000개 | 약 1.53–1.54MiB |
| 100,000개 | 약 3.11MiB |
| 100,000개 + 복원 계획 | 약 3.49MiB |

10만 개에서 **위치당 약 32.6바이트**였다. 기록과 계획을 해제한 뒤 기준값과의 차이는 약 0.2–5KiB로 돌아왔다. 문자열·소스 종류, 엔진, 배열 용량에 따라 달라지며 DevTools 전체 메모리, CDP 응답, 대상 프로세스, 브레이크포인트의 메모리는 이 숫자에 포함하지 않는다. 브라우저 전체 힙에 대한 절대 상한은 아니다.

실제 UI에서 일반 브레이크포인트로 진행한 반복문 측정:

| 방문 수 | Node: 기록 / 한 번 복원 | 브라우저 콘솔: 기록 / 한 번 복원 |
| --- | --- | --- |
| 약 4,000회 | 약 2.29초 / 2.61–2.63초 | 약 1.10초 / 1.80–1.82초 |
| 약 20,000회 | 약 10.92초 / 10.93–11.11초 | 약 4.62초 / 5.08–5.10초 |

기록 시간은 사용자 브레이크포인트 설정·Resume 조작을 포함하고, 복원 시간은 대상 재시작과 최종 UI 갱신을 포함한다. 10만 위치는 메모리 보호 상한이며, 그 규모에서 즉각적인 복원을 보장한다는 뜻은 아니다. 일반 브레이크포인트를 매번 거치는 통신 비용이 실사용의 주요 제약이다.

이전 구현은 View Transition의 비동기 콜백 안에서 재실행 전체를 기다려 화면 동결과 긴 복원의 전환 생략이 발생했다. 현재는 소스 패널만 캡처한 뒤 콜백 밖에서 재실행하고, 최종 위치가 준비되면 전환한다. 버튼 영역은 살아 있는 화면을 사용하여 로딩을 계속 표시한다. 복원 중 소스 패널의 이전 상태는 보호하지만 `document.body.inert`로 전체 화면을 차단하지 않는다. 다른 패널로 이동하면 화면 전환만 생략하고 복원 작업은 계속한다. 복원 중 사용자가 콘솔 코드를 실행하면 상태가 바뀔 수 있으므로 복원을 중단하고 이유를 안내한다.

버튼 하단 막대는 여러 기록 한도 중 가장 큰 사용 비율을 나타낸다. 80%부터 색을 바꾸고, 툴팁에 항목별 현재량과 한도를 표시한다. 이는 실제 브라우저 전체 메모리 비율이 아니다. 해제 후 막대는 0으로 돌아가며 종료 안내를 유지한다. 복원 중에는 회전 표시와 “복원 중”을 보여주고, 성공·실패 후 해제한다.

## 테스트와 검증 범위

기존 Mocha·Chai를 유지한다. 프런트엔드 단위 테스트는 Karma·Sinon, 통합 테스트는 실제 Chrome과 Node를 사용한다. React 라이브러리를 추가하지 않고 [Testing Library의 원칙](https://testing-library.com/docs/guiding-principles/)을 적용했다.

- 통합 테스트의 행동은 실제 콘솔 입력, 에디터 줄 번호 클릭, Resume·뒤로가기 버튼 클릭으로 수행한다. 제어기 메서드를 호출하여 사용자 행동을 대신하던 도우미는 제거했다.
- DOM의 버튼 상태·안내와 실제 에디터 하이라이트를 확인한다. 테스트 도우미는 소스 좌표·문서 동일성·중간 정지 전달 여부처럼 화면만으로 정밀 관찰하기 어려운 결과와 외부 재시작 연동을 담당한다.
- 순수 기록·경로 검증과 연결 경계는 공개 계약을 단위 테스트한다. 객체 재사용 여부, 중복 초기화, 폐기한 시간 만료·전용 서버 테스트는 제거했다. 공통 `break` 동작을 Node·브라우저 양쪽에서 중복 확인하던 사례도 정리했다.

저장소 루트에서 전체 빌드 후 실행한다.

```sh
nvm use
npm run build
npm test -- --skip-ninja front_end/models/replay front_end/core/sdk/DebuggerModel.test.ts
npm test -- --skip-ninja scripts/backdo/tests
```

테스트는 저장소 Chrome for Testing 경로를 기본으로 사용한다. 다른 Chrome은 `CHROME_BIN`, 별도 빌드 화면은 `BACKDO_FRONTEND_DIR`로 지정한다. 제품 사용을 위해 테스트 도우미를 실행할 필요는 없다.

개발 검증은 변경 TS를 별도 화면 디렉터리에 컴파일하여 수행했다. 단위 테스트 46개(재실행 모듈 27개와 기존 SDK를 포함한 19개), 실제 화면 통합 테스트 10개가 통과했다. 별도 실측에서는 실제 10만 위치 초과 후 기록 0개·버튼 비활성화·한국어 안내를 확인했다. 4.5초 이상의 복원 대기에서 로딩의 실제 화면 변화와 콘솔 탭 이동, 연속 복원 시 기록 수 감소도 검사한다. 변경 파일 ESLint·Stylelint, Node 테스트 TypeScript, GN 의존성 검사, GRD 리소스 목록 검사도 통과했다. 전체 프런트엔드 빌드는 사용자의 최종 확인 항목이다. 의존 파일을 포함한 TypeScript 검사에는 작업 전부터 있던 `front_end/panels/settings/KeybindsSettingsTab.ts:133` 타입 오류 한 건이 남아 있다.

## 남은 범위

- 외부 서버의 실제 포트 조회·프로세스 재시작 연결. 연동 전에는 역방향 버튼을 활성화하지 않는다.
- Node·웹페이지는 첫 정지에서 식별한 소스, 콘솔은 식별된 입력 소스를 기록한다. 다중 모듈·Worker·여러 프로세스·임의 동적 스크립트 전체의 기록은 구현하지 않았다.
- 웹페이지 검증은 결정적인 단일 스크립트 페이지다. 실제 웹 서비스의 쿠키·네트워크 응답·사용자 이벤트까지 기록·복원하지 않는다.
- Step over/out은 동기 호출 스택 깊이를 기준으로 판단한다. 비동기 경계의 모든 Step 동작이 Chrome 기본 동작과 같다고 보장하지 않는다.
- 위치 순서가 같아도 변수 값이 같다는 뜻은 아니다. 시간·난수·외부 입력·비동기 순서는 저장하지 않는다. 경로나 소스 해시가 달라지면 복원을 실패 처리한다.
- 재실행한 로그·파일 쓰기·네트워크 요청 등의 부작용은 다시 발생한다. 외부 상태를 되돌리지 않는다.
- 일시정지 중 콘솔 코드 실행, 소스 편집, 브레이크포인트 비활성화, 모든 정지 건너뛰기는 기존 기록의 신뢰성을 깨므로 뒤로가기를 중단한다.


## 상한을 정하는 근거

2026-11-09에 확인한 [Chrome 공식 메모리 가이드](https://developer.chrome.com/docs/devtools/memory-problems#memory_bloat_how_much_is_too_much)는 브라우저 앱의 보편적인 권장 MB 수치를 제시하지 않는다. 기기와 브라우저의 처리 능력이 다르므로 실제 사용자 기기에서 검사하라고 설명한다. 현재 제한값은 브라우저 권장량으로부터 산출한 값이 아니다.

- 10만 위치는 이 구현의 배열과 복원 계획을 측정한 값을 참고한 초기 상한이다. 전체 기능의 피크 메모리가 충분히 작다는 검증까지 끝난 것은 아니다.
- 콘솔 원문 4MiB, 입력·소스 256개, 브레이크포인트 2만 개는 별도로 증가할 수 있는 데이터를 제한하는 초기 정책이다. 각 상한의 충분함은 아직 검증이 필요하다.
- 상한 확정에는 최소 지원 기기, 허용할 추가 메모리와 복원 대기 시간이라는 제품 기준이 필요하다. 그 환경에서 기능을 끈 기준값과 켠 상태의 피크·GC 후 잔존량을 비교하고, 기록→복원→재기록→해제를 반복해 증가가 누적되지 않는지 확인해야 한다.
- 기록 개수만 늘리는 실험 외에도 콘솔 원문 크기와 서로 다른 정지 지점 수를 각각 늘려야 한다. 같은 줄을 2만 번 방문하는 것과 2만 개의 브레이크포인트를 설치하는 것은 비용이 다르다.

JS 힙만으로 전체 메모리를 판단하지 않는다. Chrome 가이드는 OS 메모리와 살아 있는 JS 힙을 구분한다. [web.dev의 측정 가이드](https://web.dev/articles/monitor-total-page-memory-usage)는 기존 `performance.memory`의 부정확성과, `measureUserAgentSpecificMemory()`의 브라우저·보안 조건 및 표본 측정 목적을 설명한다. 이 API를 매 이동마다 호출해 정확한 잔여 메모리처럼 표시하지 않는다. 개발 중에는 실제 Chrome의 힙 측정과 프로세스 메모리 관측을 함께 사용한다.
