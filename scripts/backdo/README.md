# BackDo의 실행 기록과 복원

BackDo는 빌드된 `devtools-frontend` 웹 화면이다. 실행 위치의 순서를 기록하고, 대상 프로세스를 처음부터 다시 실행하여 직전 위치로 돌아간다. 변수·힙·클로저의 스냅샷은 저장하지 않는다.

## 실제 사용 방법

**이번 변경은 아직 `backdo.site`에 배포되지 않았다. 아래 로컬 빌드 주소로 확인한다.** URL 단위 테스트의 `backdo.test`는 해석용 문자열이며 네트워크 요청을 하지 않는다.

프런트엔드는 이 저장소에서 독립적으로 빌드·배포한다. 프로세스 재시작 API는 별도의 `server`에서 실행한다. 두 저장소 모두 `.nvmrc`의 Node 22.11.0을 사용한다.

```sh
# devtools-frontend에서
nvm use
npm run build
python3 -m http.server 8000 --bind 127.0.0.1

# 별도 터미널의 server에서
nvm use
npm ci
npm start
```

- **기존 콘솔 사용:** server 디렉터리의 다른 터미널에서 `npm run ws`를 실행한다. 출력된 `?ws=...&backdoServer=...`를 `http://127.0.0.1:8000/out/Default/gen/front_end/devtools_app.html` 뒤에 붙여 연다. Console에 `debugger;`와 코드를 입력한다.
- **Node 사용:** 사용자가 자신의 터미널에서 `node --inspect-brk <cli.js> [인자...]`를 실행한다. `http://127.0.0.1:8000/out/Default/gen/front_end/js_app.html?port=9229`를 연다. 파일 경로나 실행 명령을 BackDo에 전달하지 않는다.
- **기존 Node 주소:** `/json/list`에서 얻은 `js_app.html?ws=127.0.0.1:9229/<ID>`도 지원한다.
- **웹페이지:** 서버가 생성한 브라우저의 ws로 `inspector.html?ws=...`에 연결한다. 대상 페이지로 이동한 뒤 같은 공통 복원 엔진을 사용한다.

8000은 사용자가 여는 화면 포트의 예시다. 프런트엔드의 정적 서버나 배포 위치는 자유롭게 선택한다. API 서버는 프런트엔드 파일을 제공하지 않는다. API 포트는 `BACKDO_SERVER_PORT`로 지정하며, 기본 3000이 아닌 API를 사용하면 화면 주소에 `backdoServer=http://127.0.0.1:<서버 포트>`를 붙인다.

| 입력·동작 | 실제 연동 |
| --- | --- |
| `?port=9229` | 서버가 해당 포트의 `/json/list`를 조회하고 Node 세션 등록 |
| `?ws=...` | 로컬 서버에 같은 대상을 등록한 뒤 연결; 서버가 없으면 일반 디버깅만 유지 |
| 최초 정지 | 서버가 Node 실행 정보를 조회하고, 별도 더미를 실제 생성하여 CDP 비용 측정 |
| 뒤로가기 | 기존 프로세스 종료 확인 → 같은 포트로 재시작 → 새 ws로 연결 교체 |
| 측정 실패·재시작 연동 없음 | 뒤로가기 버튼 비활성화와 사유 표시 |

`LocalTargetLifecycle`이 실제 HTTP 연결을 맡고 `ReplayConnection`·`ReplayController`는 콘솔·Node·inspector가 공유한다. 통합 테스트도 제품의 서버 API를 호출하며 테스트용 lifecycle을 주입하지 않는다. 포트만으로 브라우저 JavaScript가 OS 프로세스를 제어할 수는 없으므로 로컬 서버가 필요하다.

화면을 별도로 배포할 때는 API 서버의 `BACKDO_ALLOWED_ORIGINS`에 배포 출처를 추가할 수 있다. 이 작업에는 운영 사이트 배포가 포함되지 않는다. [Chrome의 로컬 네트워크 접근 권한](https://developer.chrome.com/blog/local-network-access)이 필요한 환경에서는 허용해야 한다. 로컬 개발에서도 화면과 API는 다른 출처이며, 서버가 로컬 화면의 API 접근을 허용한다.

## Node 실행 정보의 보존 범위

서버는 첫 `Debugger.paused`에서 `Runtime.evaluate`로 `process`의 실행 정보를 읽는다. 디버거 부트스트랩 중에는 `argv`가 준비되지 않을 수 있으므로 사용자가 `--inspect-brk`로 실행한 첫 정지를 기준으로 한다. 조회를 위해 사용자 코드를 재개하거나 재시작하지 않는다.

- `execPath`, `argv0`, **argv 전체·execArgv 전체·환경변수 전체**, 작업 폴더, umask, 유효 사용자·그룹 ID를 서버 메모리에 보관한다. HTTP 응답에는 세션 ID·PID·포트·ws만 내보낸다.
- 재시작 시 디버거 옵션은 같은 포트의 `--inspect-brk`로 바꾼다. 다른 Node 옵션과 공백·빈 문자열을 포함한 프로그램 인자는 유지한다. umask 전달용 내부 옵션과 환경변수는 사용자 코드 진입 전에 제거하거나 원래 값으로 복구한다.
- `process` 객체 자체, 변수·힙, 열린 파일·소켓·IPC·기존 터미널 입력 핸들은 복제하지 않는다. 재시작된 프로그램의 출력은 서버 터미널로 전달하고 표준 입력은 연결하지 않는다. 입력 대기형 CLI는 현재 지원 범위가 아니다.
- 뒤늦게 연결하면 이미 바뀐 환경·작업 폴더를 읽을 수 있다. 원래 셸의 과거 상태를 추론하지 않는다. Worker·자식 프로세스 트리·권한 제한 옵션·사용자 preload의 모든 조합은 검증하지 않았다.

서버는 살아 있는 CDP 연결로 PID를 확인한 뒤 먼저 프로세스를 종료한다. ws를 먼저 끊으면 일시정지한 Node가 재개될 수 있으므로 이 순서를 지킨다. 새 프로세스가 디버거를 연 뒤 프런트엔드의 실제 연결과 주소를 함께 바꾼다.

## 공통 실행 흐름

```text
기존 콘솔 / Node ws 연결 / inspector 웹페이지
                         ↓
        ReplayConnection: 대상과 연결 구성
                         ↓
    ReplayController: 일반 브레이크포인트 설치
                         ↓
    ReplaySession: 위치·순서 기록, Step·Resume 판단
                         ↓
          뒤로가기 버튼 → 직전 위치 선택
                         ↓
  로컬 서버가 대상 재시작 → 새 WebSocket에 연결
                         ↓
     같은 문서에서 history.replaceState로 주소 갱신
                         ↓
 콘솔 원문 다시 제출 / 웹페이지 이동 / Node 실행 재개
                         ↓
     매 정지의 소스 해시·줄·열·순서를 기록과 대조
                         ↓
        목표 정지만 UI에 전달하고 화면 전환
```

`history.replaceState`는 실제 연결이 응답한 뒤 적용한다. BackDo 문서와 `history.state`를 유지한다. 중간 정지는 SDK에서 소비하므로 Sources 패널에는 최종 정지만 전달한다.

브라우저와 Node가 별도 복원 엔진을 갖지 않는다. 대상별 차이는 연결 종류와 시작 입력에 한정한다. 웹페이지 재시작은 기존 페이지 URL로 다시 이동하며, 콘솔 입력은 원문과 입력 시점을 다시 제출한다. 콘솔에서 먼저 준비 코드를 실행한 뒤 디버깅 코드를 입력하는 경우도 테스트했다.

## 기록의 수명과 용량

기록은 **프런트엔드 메모리**에만 보관한다. 시간 경과나 장시간 일시정지만으로 만료하지 않는다. 실행 컨텍스트 교체, 새 대상 연결, 종료·실패 때 해제한다. 제어된 복원을 위한 재연결에서는 목표에 도달할 때까지 유지한다.

| 항목 | 상한 | 의미 |
| --- | ---: | --- |
| 예상 CDP 처리 시간 | 3초 미만 | 더미 요청 한 번의 왕복 실측 × 현재 방문 기록 개수 |
| 방문한 실행 위치 | 100,000개 | 별도의 메모리 보호 상한. 같은 위치를 반복 방문해도 각각 계산 |
| 콘솔 입력 | 256개 | 이전 입력도 순서대로 재실행하기 위한 원문 |
| 콘솔 원문 | 4MiB | `문자열.length × 2`로 산정한 예산; 실제 힙과 동일하지 않음 |
| 기록용 브레이크포인트 | 20,000개 | 서로 다른 정지 가능 위치 |
| 식별 대기·보관 중인 콘솔 소스 | 256개 | 익명 스크립트 식별 결과의 누적 제한 |

예상 시간이 3초 이상이거나 용량 상한 중 하나를 넘으면 위치·복원 계획·콘솔 원문·소스 매핑을 함께 해제하고 기록용 브레이크포인트를 제거한다. 앞부분만 지우면 처음부터의 경로를 검증할 수 없으므로 **해당 실행 기록 전체를 종료**한다. 일반 디버깅은 계속 사용할 수 있고, 뒤로가기는 비활성화한다. 툴팁과 오류 안내에는 다음 사유가 들어간다.

> 실행 기록 한도에 도달해 뒤로가기를 사용할 수 없습니다. 뒤로가기가 필요하면 디버깅 세션을 다시 시작하고, 가능하면 실행 범위를 줄여 원하는 위치까지 이동해 주세요.

Resume도 내부에서는 모든 방문 위치를 기록한다. 따라서 클릭 수를 줄이는 것만으로 기록량이 줄어들지는 않는다. 입력 데이터·반복 횟수·실행 경로를 줄이는 것이 도움이 된다. **소스 1,000줄과 위치 1,000회 방문은 다르다.** 짧은 반복문도 많은 기록을 만들 수 있다.

복원 중 30초 동안 진행이 없으면 응답 없는 연결·대기 작업을 실패 처리한다. 진행이 있으면 대기 제한을 갱신한다. 이것은 기록의 보관 시간이나 복원 총시간 제한이 아니다.

## 측정 결과

Node 22.11.0, macOS arm64, Chrome 156.0.8078.81에서 측정했다. 측정 결과는 이 환경의 표본이며 모든 기기의 보장은 아니다.

위치 배열의 증분 힙은 실제 Chrome에서 `HeapProfiler.collectGarbage` 이후 `Runtime.getHeapUsage`로 3회 측정했다. 같은 소스의 URL·해시 문자열을 공유하는 경우다. 모듈 로딩과 초기 실행 비용을 제외한 기준값 대비 증가량이다.

| 방문 위치 수 | 위치 배열의 증분 힙 |
| --- | ---: |
| 1,000개 | 약 33–37KiB |
| 10,000개 | 약 318–322KiB |
| 50,000개 | 약 1.53–1.54MiB |
| 100,000개 | 약 3.11MiB |
| 100,000개 + 복원 계획 | 약 3.49MiB |

10만 개에서 **위치당 약 32.6바이트**였다. 기록과 계획을 해제한 뒤 기준값과의 차이는 약 0.2–5KiB로 돌아왔다. 문자열·소스 종류, 엔진, 배열 용량에 따라 달라지며 DevTools 전체 메모리, CDP 응답, 대상 프로세스, 브레이크포인트의 메모리는 이 숫자에 포함하지 않는다. 브라우저 전체 힙에 대한 절대 상한은 아니다.

실제 UI에서 일반 브레이크포인트로 진행한 반복문 측정:

| 방문 수 | Node: 기록 / 한 번 복원 | 브라우저 콘솔: 기록 / 한 번 복원 |
| --- | --- | --- |
| 약 4,000회 | 약 2.29초 / 2.61–2.63초 | 약 1.10초 / 1.80–1.82초 |
| 약 20,000회 | 약 10.92초 / 10.93–11.11초 | 약 4.62초 / 5.08–5.10초 |

위 표는 시간 예산 적용 전의 측정이다. 기록 시간은 사용자 브레이크포인트 설정·Resume 조작을 포함하고, 복원 시간은 대상 재시작과 최종 UI 갱신을 포함한다. 약 4천 회를 현재 화면 전환에서 다시 측정한 Node 4개 표본은 2.672–2.867초였다. 기록 개수 하나로 모든 환경의 3초 미만 복원을 보장할 수 없어, 아래의 CDP 비용 추정 정책을 적용했다. 이 지표는 전체 복원 시간과 구분한다.

이전 구현은 View Transition의 비동기 콜백 안에서 재실행 전체를 기다려 화면 동결과 긴 복원의 전환 생략이 발생했다. 현재는 소스 패널만 캡처한 뒤 콜백 밖에서 재실행하고, 최종 위치가 준비되면 전환한다. 버튼 영역은 살아 있는 화면을 사용하여 로딩을 계속 표시한다. 복원 중 소스 패널의 이전 상태는 보호하지만 `document.body.inert`로 전체 화면을 차단하지 않는다. 다른 패널로 이동하면 화면 전환만 생략하고 복원 작업은 계속한다. 복원 중 사용자가 콘솔 코드를 실행하면 상태가 바뀔 수 있으므로 복원을 중단하고 이유를 안내한다.

버튼 하단 막대는 예상 CDP 처리 시간/3초와 여러 용량 한도 중 가장 큰 사용 비율을 나타낸다. 툴팁에는 예상 CDP 처리 시간과 제외되는 비용을 표시한다. 80%부터 색을 바꾸고, 툴팁에 항목별 현재량과 한도를 표시한다. 이는 실제 브라우저 전체 메모리 비율이 아니다. 해제 후 막대는 0으로 돌아가며 종료 안내를 유지한다. 복원 중에는 회전 표시와 “복원 중”을 보여주고, 성공·실패 후 해제한다.

## 사용자 코드 실행 없는 CDP 비용 측정

최초 정지를 기록하면 **사용자 대상과 별도의 OS 프로세스·포트**를 생성하도록 로컬 서버에 요청한다. 브라우저 JavaScript 자체가 OS 프로세스를 실행하지 않는다. 생성자가 소유한 더미를 반환해야 하며, 생성 실패·취소 시 생성자도 자원을 정리해야 한다. `dispose()`는 해당 더미만 종료하고 중복 호출에도 안전해야 한다.

```text
사용자 대상 → 위치 기록 N개 ──────────────────┐
                                            ↓
별도 더미 생성 → 독립 WebSocket → 고정 소스 컴파일
                      ↓                     ↓
           getPossibleBreakpoints 1회 왕복 T → T × N
                      ↓                     ↓
            더미 연결·프로세스 종료        3,000ms 이상이면 기록 종료
```

- `ReplayCalibration`은 사용자 소스·좌표를 받지 않는다. 고정 더미를 `Runtime.compileScript`로 준비하고 `Debugger.getPossibleBreakpoints` 한 번의 전송부터 응답 처리까지 `performance.now()`로 측정한다. `evaluate`·`runScript`·`resume`은 보내지 않는다. 사용자 주소는 잘못된 동일 포트 연결을 거부하는 데만 사용한다.
- [CDP의 `getPossibleBreakpoints`](https://chromedevtools.github.io/devtools-protocol/tot/Debugger/#method-getPossibleBreakpoints)는 주어진 소스 범위의 정지 가능 위치를 반환한다. [컴파일](https://chromedevtools.github.io/devtools-protocol/tot/Runtime/#method-compileScript)과 실행은 별도 명령이다. 실제 사용자 기록의 줄·열·scriptId를 더미 위치로 사용하지 않는다.
- 측정은 전역 SDK 연결·대상 목록·사용자 WebSocket·주소·Sources 화면에 참여하지 않는다. 사용자 대상의 재시작·재개·콘솔 재실행 없이 수행한다. “측정 중”에도 Resume·Step은 사용할 수 있다. 뒤로가기만 측정 완료 전까지 비활성화한다.
- 성공·실패·취소 시 더미 연결과 소유 프로세스를 정리한다. 세션이 끝난 뒤 늦게 생성된 더미도 종료하고, 이전 세션의 결과를 새 세션에 적용하지 않는다. 30초는 응답 없는 측정을 정리하는 제한이며 기록 보관 시간이나 3초 예산과 다르다.
- 측정값은 세션마다 한 번 구한다. 조회 한 번의 시간이 0이나 유효하지 않은 값이면 임의 기본값을 사용하지 않고 실패를 안내한다. 측정 연동이 없으면 사용자 대상으로 대체 측정하지 않는다.
- 예상 CDP 비용은 **왕복 시간 × 현재 기록 개수**다. 같은 위치의 반복 방문도 개수에 포함하며 복원으로 미래 기록을 버리면 비용도 감소한다. 사용자 코드 계산·`await`·읽는 시간, 초기 1초, 25% 여유, 실제 복원 완료 시간을 이 식에 섞지 않는다. 측정용 위치별 시간 배열이나 상태 스냅샷도 저장하지 않는다.
- 예상 CDP 비용이 3초 이상이면 기록 전체를 해제하고 사유를 표시한다. 이미 시작한 복원을 3초에 강제 종료하지 않는다. 느린 재시작 뒤에도 실제 대기 시간을 CDP 왕복 측정값으로 바꾸지 않는다.

**이 값은 전체 복원 시간의 보장값이 아니다.** 한 번의 `getPossibleBreakpoints` 응답에는 그 명령의 처리 비용도 포함되므로 순수 네트워크 지연이나 `resume → paused` 비용과 같다고 입증한 값은 아니다. 요청 한 번을 기록 하나의 대표 비용으로 쓰는 추정 정책이다. 재시작·연결·지점 설치·코드 실행·비동기 대기·화면 표시 비용은 제외한다. 단일 표본은 시계 해상도·기기 부하에 따라 달라질 수 있다. 사용자 코드를 추가 실행하지 않는 정책과 실제 복원 3초 보장은 구분한다.

검증 환경에서 더미 측정 10회는 0.2–0.7ms였고 사용자 대상 재시작은 0회, 더미 생성·종료는 각각 10회였다. 외부 요청을 수행하는 콘솔 준비 코드도 요청 수 1회를 유지했다. 예를 들어 기록 21개의 예상 CDP 비용은 약 4.2ms였지만, 실제 전체 복원은 약 577ms였다. 두 시간을 같은 의미로 표시하지 않는 이유다. 이 수치는 해당 기기·단일 표본의 결과이며 지원 성능 보장값이 아니다.

## 테스트와 검증 범위

기존 Mocha·Chai를 유지한다. 프런트엔드 단위 테스트는 Karma·Sinon, 통합 테스트는 실제 Chrome과 Node를 사용한다. React 라이브러리를 추가하지 않고 [Testing Library의 원칙](https://testing-library.com/docs/guiding-principles/)을 적용했다.

- 통합 테스트의 행동은 실제 콘솔 입력, 에디터 줄 번호 클릭, Resume·뒤로가기 버튼 클릭으로 수행한다. 제어기 메서드를 호출하여 사용자 행동을 대신하던 도우미는 제거했다.
- DOM의 버튼 상태·안내와 실제 에디터 하이라이트를 확인한다. 테스트 도우미는 소스 좌표·문서 동일성·중간 정지 전달 여부처럼 화면만으로 정밀 관찰하기 어려운 결과의 관찰만 담당한다. 재시작과 더미 생성은 실제 서버가 수행한다.
- 순수 기록·경로 검증과 연결 경계는 공개 계약을 단위 테스트한다. 객체 재사용 여부, 중복 초기화, 폐기한 시간 만료·전용 서버 테스트는 제거했다. 공통 `break` 동작을 Node·브라우저 양쪽에서 중복 확인하던 사례도 정리했다.

저장소 루트에서 전체 빌드 후 실행한다.

```sh
nvm use
npm run build
npm test -- --skip-ninja front_end/models/replay front_end/core/sdk/DebuggerModel.test.ts
npm test -- --skip-ninja scripts/backdo/tests
```

통합 테스트 전 형제 `server`에서 `npm ci`를 실행한다. 다른 서버 저장소 경로는 `BACKDO_SERVER_DIR`로 지정한다. 테스트는 화면과 API를 서로 다른 임시 포트에서 제공한다. 저장소 Chrome for Testing 경로를 기본으로 사용하며 다른 Chrome은 `CHROME_BIN`으로 지정한다. `BACKDO_FRONTEND_DIR`는 테스트용 정적 서버가 읽을 빌드 폴더를 지정하는 환경변수다. 제품 API 서버의 설정이 아니다. 제품 사용을 위해 테스트 도우미를 실행할 필요는 없다.

개발 검증은 변경 TS를 별도 화면 디렉터리에 컴파일하여 수행했다. 프런트엔드 Mocha·Chai 단위 테스트 55개, 실제 화면 통합 테스트 12개, 서버 Mocha·Chai 테스트 6개가 통과했다. 서버 실행 파일과 기존 ws·close 명령의 실행도 확인했다. 변경 파일 ESLint, Node 테스트 TypeScript, GN 의존성과 GRD 리소스 검사도 통과했다. 실제 Node·브라우저 콘솔·inspector 경로에서 더미와 사용자의 PID·포트가 다르고, 측정 후 사용자 PID·WebSocket·위치·문서가 유지되는지 확인한다. 콘솔 준비 코드의 외부 요청이 측정 때문에 반복되지 않는지도 확인한다. `for`·`async/await`·`for...of`·연속 뒤로가기·화면 전환 검증은 유지한다. 실패·늦은 취소·3초 기준의 기록 해제도 별도로 검사한다.

전체 프런트엔드 빌드는 사용자의 최종 확인 항목이다. 의존 파일을 포함한 TypeScript 검사에는 작업 전부터 있던 `front_end/panels/settings/KeybindsSettingsTab.ts:133` 타입 오류 한 건이 남아 있다.

## 남은 범위

- 외부에서 별도로 실행한 Chrome의 재시작은 지원하지 않는다. 현재는 이 서버가 만든 브라우저를 관리한다.
- Node·웹페이지는 첫 정지에서 식별한 소스, 콘솔은 식별된 입력 소스를 기록한다. 다중 모듈·Worker·여러 프로세스·임의 동적 스크립트 전체의 기록은 구현하지 않았다.
- 웹페이지 검증은 결정적인 단일 스크립트 페이지다. 실제 웹 서비스의 쿠키·네트워크 응답·사용자 이벤트까지 기록·복원하지 않는다.
- Step over/out은 동기 호출 스택 깊이를 기준으로 판단한다. 비동기 경계의 모든 Step 동작이 Chrome 기본 동작과 같다고 보장하지 않는다.
- 위치 순서가 같아도 변수 값이 같다는 뜻은 아니다. 시간·난수·외부 입력·비동기 순서는 저장하지 않는다. 경로나 소스 해시가 달라지면 복원을 실패 처리한다.
- 재실행한 로그·파일 쓰기·네트워크 요청 등의 부작용은 다시 발생한다. 외부 상태를 되돌리지 않는다.
- 일시정지 중 콘솔 코드 실행, 소스 편집, 브레이크포인트 비활성화, 모든 정지 건너뛰기는 기존 기록의 신뢰성을 깨므로 뒤로가기를 중단한다.


## 상한을 정하는 근거

2026-11-09에 확인한 [Chrome 공식 메모리 가이드](https://developer.chrome.com/docs/devtools/memory-problems#memory_bloat_how_much_is_too_much)는 브라우저 앱의 보편적인 권장 MB 수치를 제시하지 않는다. 기기와 브라우저의 처리 능력이 다르므로 실제 사용자 기기에서 검사하라고 설명한다. 현재 제한값은 브라우저 권장량으로부터 산출한 값이 아니다.

- 제품의 기준은 **뒤로가기 클릭부터 최종 위치 표시와 화면 전환 완료까지 3초 미만**이다. 이는 사용자가 정한 제품 기준이며, 모든 사용자가 정확히 3초에 이탈한다는 연구 결과를 주장하지 않는다.
- 10만 위치는 메모리 보호를 위한 최후의 상한이다. 실제 기록은 기기별 예상 CDP 처리 비용이 먼저 3초에 도달하면 종료한다. 전체 기능의 피크 메모리가 충분히 작다는 검증까지 끝난 것은 아니다.
- 콘솔 원문 4MiB, 입력·소스 256개, 브레이크포인트 2만 개는 별도로 증가할 수 있는 데이터를 제한하는 초기 정책이다. 각 상한의 충분함은 아직 검증이 필요하다.
- 복원 대기 시간 기준은 3초 미만으로 정했다. 보장 범위를 확정하려면 최소 지원 기기와 허용할 추가 메모리 기준이 여전히 필요하다. 그 환경에서 기능을 끈 기준값과 켠 상태의 피크·GC 후 잔존량을 비교하고, 기록→복원→재기록→해제를 반복해 증가가 누적되지 않는지 확인해야 한다.
- 기록 개수만 늘리는 실험 외에도 콘솔 원문 크기와 서로 다른 정지 지점 수를 각각 늘려야 한다. 같은 줄을 2만 번 방문하는 것과 2만 개의 브레이크포인트를 설치하는 것은 비용이 다르다.

JS 힙만으로 전체 메모리를 판단하지 않는다. Chrome 가이드는 OS 메모리와 살아 있는 JS 힙을 구분한다. [web.dev의 측정 가이드](https://web.dev/articles/monitor-total-page-memory-usage)는 기존 `performance.memory`의 부정확성과, `measureUserAgentSpecificMemory()`의 브라우저·보안 조건 및 표본 측정 목적을 설명한다. 이 API를 매 이동마다 호출해 정확한 잔여 메모리처럼 표시하지 않는다. 개발 중에는 실제 Chrome의 힙 측정과 프로세스 메모리 관측을 함께 사용한다.
